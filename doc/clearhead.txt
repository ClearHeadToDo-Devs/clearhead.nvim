==============================================================================
1. INTRODUCTION                                             *clearhead-intro*

clearhead.nvim is a thin-client Neovim plugin for the ClearHead personal
action management platform. It works with `.actions` files — a plaintext
DSL for capturing and organising work items.

The plugin delegates durable mutations such as archiving to the `clearhead`
CLI, graph reads to `clearhead-graphd`, and editor analysis/formatting to the
standalone `clearhead-lsp` server.
Local operations that benefit from low
latency (state cycling, smart insertion, statusline counts) run directly via
tree-sitter, so they work even offline or before the CLI is installed.

The workspace is plain text on disk. It will always be readable without
any tooling, and every file is safe to commit to version control.

==============================================================================
2. REQUIREMENTS                                        *clearhead-requirements*

  - Neovim 0.10+
  - tree-sitter support enabled
  - `nvim-treesitter` with the `actions` grammar installed
  - `clearhead` CLI for durable mutations
  - `clearhead-graphd` for query views
  - `clearhead-lsp` for document intelligence
    Build source from each sibling repository with `cargo build`.

3. SETUP                                                    *clearhead-setup*

Install with any plugin manager. Example using lazy.nvim: >lua

  {
    "ClearHeadToDo-Devs/clearhead.nvim",
    ft = { "actions", "markdown" },
    cmd = {
      "ClearheadInbox",
      "ClearheadWorkspace",
      "ClearheadProjectRoot",
      "ClearheadDiff",
      "ClearheadArchiveWorkspace",
      "ClearheadPickActions",
      "ClearheadPickCharters",
      "ClearheadQuery",
    },
  }
<
The plugin works without calling `setup()`. Commands are registered from
`plugin/`, and buffer-local behavior is applied from `ftplugin/`.

Call `setup({})` only when you want Lua-side overrides in addition to the
shared ClearHead config file and environment variables.
See |clearhead-config| for all available keys.

Verify installation: >vim

  :checkhealth clearhead
<

4. CONFIGURATION                                           *clearhead-config*

Pass options to `setup()` only when you want to override config from Lua.
All keys are optional; defaults shown below. >lua

  require("clearhead").setup({
    -- Core (shared with CLI via ~/.config/clearhead/config.json)
    data_dir              = "",    -- workspace root (XDG default)
    config_dir            = "",    -- config directory (XDG default)
    default_file          = "inbox.actions",
    additional_workspaces = {},      -- extra workspace roots for pickers/LSP

    -- Neovim-specific
    nvim_auto_normalize   = true,      -- add missing UUIDs on save
    nvim_format_on_save   = true,      -- format on BufWritePre via LSP
    nvim_lsp_enable       = true,      -- auto-start clearhead-lsp
    nvim_lsp_binary_path  = "",        -- explicit clearhead-lsp path (auto-detected)
    nvim_graphd_binary_path = "",      -- explicit clearhead-graphd path (auto-detected)
    nvim_inbox_file       = "",        -- override inbox path
    nvim_default_mappings = true,      -- enable <localleader> keybindings
    nvim_indent_style     = "spaces", -- buffer-local indent style
    nvim_indent_width     = 4,         -- buffer-local indent width
  })
<
                                                        *clearhead-config-xdg*
XDG defaults ~

  data_dir    →  $XDG_DATA_HOME/clearhead   (~/.local/share/clearhead)
  config_dir  →  $XDG_CONFIG_HOME/clearhead (~/.config/clearhead)

Configuration is loaded in this order (later values win):
  1. Plugin defaults
  2. `~/.config/clearhead/config.json`
  3. Environment variables
  4. Keys passed to `setup()`

Without `setup()`, the plugin still uses the first three layers and works
normally.

                                                    *clearhead-config-bin-path*
Binary path resolution ~

The plugin resolves the LSP process command in this order:
  1. `nvim_lsp_binary_path` if set and executable
  2. `clearhead-lsp` on `$PATH`
  3. `~/.cargo/bin/clearhead-lsp`
  4. temporary compatibility fallback: `clearhead start lsp`

The graph query tool resolves independently through `nvim_graphd_binary_path`,
`clearhead-graphd` on `$PATH`, then `~/.cargo/bin/clearhead-graphd`. The
synchronous mutation client similarly resolves as `clearhead` on `$PATH`, then
`~/.cargo/bin/clearhead`. Configuring one tool never redirects another tool's
commands.

5.1 FIRST CAPTURE                                      *clearhead-tut-capture*

Open the inbox in the current window: >vim

  :ClearheadInbox
<
Or from any `.actions` buffer: `<localleader>i`

The inbox lives at `data_dir/charters/inbox.actions`. It is the default
landing zone for anything that has not been sorted into a charter yet.

Write your first action — just a state and a name: >

  [ ] buy oat milk
<
Save the file. On save, the LSP (or CLI fallback) assigns a UUID and
normalises spacing: >

  [ ] buy oat milk ^2026-05-17T14:30 #019eabcd-...
<
The `^` timestamp records when the action was created. The `#` field is
the stable UUID that lets other actions reference this one and lets the
system track it across renames.

You do not need to type either field by hand. Format-on-save handles both.

------------------------------------------------------------------------------
5.2 THE ACTIONS FORMAT                                  *clearhead-tut-format*

A `.actions` file is a list of actions. Every action starts with a state
marker. Fields follow in any order (the formatter will sort them on save).

States ~

  `[ ]`   Not started
  `[-]`   In progress
  `[=]`   Blocked / awaiting something
  `[x]`   Completed
  `[_]`   Cancelled

Fields (all optional except state and name) ~

  `=alias`            Stable short name for cross-references
  `$ ... $`           Multi-line description block (see below)
  `~`                 Sequential children — children must be done in order
  `!<n>`              Priority (1 = highest urgency)
  `*<ref>`            Objective or parent reference (`*work/clearhead/docs`)
  `+<tag>`            Context tag (`+work`, `+home,errand`)
  `@<datetime>`       Do date — when you intend to work on this
  `:<datetime>`       Due date — hard deadline
  `^<datetime>`       Created timestamp (assigned automatically)
  `%<datetime>`       Completed timestamp (assigned when state → x)
  `#<uuid>`           Stable identifier (assigned automatically)
  `<<ref>`            Predecessor — must be closed before this is unblocked

A complete example: >

  [-] Ship v1.0 release =ship-v1 !1 *clearhead @2026-06-01T09:00
      $ Final release checklist. All children sequential. $
      ~ +work ^2026-05-01T10:00 #019eabcd-1234-...
  > [ ] Run test suite !2 +ci
  > [ ] Build binary !1
  > [ ] Tag release !1 < build-binary
  > [ ] Publish to crates.io !1
  > [ ] Announce !3
<
Descriptions ~

A description block opens and closes with `$`: >

  [ ] Weekly review
      $ Review all open actions. Check in with
        project charters. Update priorities.
      $
<
Inline description (single line): >

  [ ] Buy coffee $ dark roast, whole bean $
<
Dates ~

Dates follow ISO 8601. All of these are valid: >

  @2026-05-17
  @2026-05-17T14:30
  @2026-05-17T14:30:00
<
Time zones are optional; local time is assumed when omitted.

Objective references ~

`*` links an action to an objective. Use path notation to reference nested
objectives: >

  [ ] Write ADR for new auth scheme *work/clearhead/architecture
<
Context tags ~

Tags are prefixed with `+`. Multiple tags can be comma-separated: >

  [ ] Grocery run +home,errand @2026-05-18
<
Predecessors ~

`<ref>` marks a dependency. The action is blocked until the predecessor is
closed. Reference by alias, UUID prefix, or name: >

  [ ] Deploy to production < run-migrations =deploy-prod
<
Aliases ~

`=alias` gives an action a stable short name for references. Aliases must
be unique within the workspace: >

  [ ] Run database migrations =run-migrations !1
<

5.3 CHILDREN AND DEPTH                                    *clearhead-tut-depth*

Children are indented with `>` markers. One `>` = depth 1, `>>` = depth 2,
and so on. Whitespace before the marker is cosmetic and does not affect
parsing — use it for visual alignment.

By default `clearhead.nvim` sets buffer-local indentation for `.actions`
files to 4 spaces (`expandtab`, `shiftwidth=4`, `tabstop=4`,
`softtabstop=4`). The LSP formatter uses those live buffer settings, so
formatted child actions follow the current editor indentation style.

A parent action and its children: >

  [ ] Plan team offsite
  >[ ] Book venue @2026-06-10
  >[ ] Arrange travel
  >>[ ] Book flights
  >>[ ] Book hotels
  >[ ] Send invites @2026-06-12
<
Keyboard shortcuts for depth changes ~

  `>>`   Increase depth of action on current line (adds one `>`)
  `<<`   Decrease depth of action on current line (removes one `>`)

These map over the built-in Vim indent commands for `.actions` buffers.
The LSP will flag invalid depth transitions (such as skipping a level)
on the next save.

Creating a sibling action ~

  `<localleader>o`   Insert a new `[ ]` below the current line at the
                     same depth. A `^` creation timestamp is added; the
                     UUID is assigned on save.

Sequential children ~

Add `~` to a parent to mark its direct children as sequentially ordered.
The LSP surfaces a warning if they are completed out of order: >

  [ ] Morning routine ~
  >[ ] Wake up
  >[ ] Shower
  >[ ] Breakfast
<

5.4 DAILY WORKFLOW                                     *clearhead-tut-workflow*

A typical day with clearhead.nvim looks like this:

1. CAPTURE
   Jump to the inbox with `<localleader>i` (or `:ClearheadInbox`) and
   dump everything you need to do. Don't worry about organisation yet.
   One action per line; state is `[ ]`. Save; UUIDs are assigned. >

     [ ] reply to Alice's email +work
     [ ] pick up prescription +health @2026-05-18
     [ ] review PR #412 +work
<

2. TRIAGE
   Open the picker with `<localleader>s` to jump to the charter where
   each item belongs, or use `<localleader>i` to stay in the inbox.

   Set priorities with `!` fields. Add `@` do-dates where helpful.
   Use `<localleader><space>` to cycle states as you triage:

     `[ ]` → `[-]` → `[=]` → `[x]` → `[_]` → `[ ]`

3. ACT
   Work through the day. Use `<localleader>-` to mark items in progress.
   Use `<localleader>x` to complete them. The `%` completion timestamp
   is appended automatically.

4. REVIEW
   At the end of the day (or week), check the statusline count.
   `get_status()` returns `✓ completed/total` for the current file.
   See |clearhead-statusline|.

5. ARCHIVE
   When a file accumulates many completed items, press `<localleader>a`
   to sweep them to `<charter>.completed.actions`. See |clearhead-tut-archive|.

State cycling reference ~

  `<localleader><space>`   Cycle through all states in order
  `<localleader>x`         Complete (single action)
  `<localleader>X`         Complete action AND all its children recursively
  `<localleader>-`         Mark in progress
  `<localleader>=`         Mark blocked/awaiting
  `<localleader>_`         Cancel
  `<localleader><bs>`      Reset to not started

5.5 CHARTERS                                          *clearhead-tut-charters*

A charter is a named domain of concern — roughly equivalent to a project,
area of responsibility, or theme. Each charter gets its own `.actions` file.

Workspace layout ~
>
  ~/.local/share/clearhead/
  ├── archive/                 ← archived charter/action plaintext
  ├── charters/
  │   ├── inbox.actions        ← uncategorised captures
  │   ├── work.actions         ← a flat charter
  │   ├── health.actions
  │   ├── financial/           ← directory-form charter
  │   │   ├── README.md        ← charter description / metadata
  │   │   └── next.actions     ← the charter's active actions
  │   └── financial/
  │       └── taxes.actions    ← sub-charter inside financial/
  ├── objectives/
  └── plans/
<
Flat charters use a single file (`health.actions`). Directory-form charters
are a folder with `next.actions` as the entry point and an optional
`README.md` carrying frontmatter (alias, state, description).

Each charter can also have:
  `<charter>.completed.actions`  — completed/cancelled actions
  `<charter>.upcoming.actions`   — future generated instances from plans

Navigation ~

  `<localleader>i`   Open inbox
  `<localleader>s`   Picker over all active action files
  `<localleader>S`   Picker over all markdown charter documents
  `<localleader>p`   Open workspace data directory (netrw / oil.nvim / etc.)
  `<localleader>P`   Walk up from current buffer, open nearest `next.actions`

The pickers (`<localleader>s` / `<localleader>S`) use `vim.ui.select` and
automatically delegate to telescope, fzf-lua, or snacks.nvim if installed,
giving you fuzzy search over all charter names with no extra configuration.

When multiple workspaces are visible (global, ancestor projects, sibling
repos in a higher-order workspace, or configured extras), each label is
prefixed `[scope]` — e.g. `[~] health` vs `[platform] health` — so fuzzy
search distinguishes them cleanly.

Picker discovery is recursive under `charters/`, so nested charter
hierarchies are included rather than only top-level files.

For root-charter files like `charters/next.actions`, picker labels use the
workspace / project name rather than the literal directory name `charters`.

Charter markdown files ~

A `<charter>.md` or `README.md` carries YAML frontmatter: >yaml

  ---
  alias: financial
  state: Active
  description: Personal finance tracking
  ---
<
`state: Closed` is required before the charter can be archived (see
|clearhead-tut-archive|). Use `<localleader>S` to jump to the markdown file
and edit it.

When you are inside a charter markdown file, charter-scoped mappings remain
available there too: `<localleader>A`, `<localleader>C`, `<localleader>s`,
`<localleader>S`, `<localleader>p`, `<localleader>P`, and `<localleader>i`.

------------------------------------------------------------------------------
5.6 PROJECT WORKSPACES                                 *clearhead-tut-projects*

Any directory containing a `.clearhead/` folder is a project workspace.
The plugin walks upward from the current buffer to find the nearest one.

Project workspace layout ~
>
  my-project/
  └── .clearhead/
      ├── charters/
      │   ├── next.actions       ← root charter for the project
      │   ├── backend.actions
      │   └── frontend/
      │       └── next.actions
      ├── objectives/
      └── plans/
<
Create a project workspace: >sh

  mkdir -p my-project/.clearhead/charters
  touch my-project/.clearhead/charters/next.actions
<
Open the project root from any buffer inside the project: >vim

  <localleader>P
<
or >vim

  :ClearheadProjectRoot
<
The plugin walks upward from the current file's directory until it finds
`.clearhead/`, then opens `charters/next.actions`. If none is found, it
falls back to the global inbox.

The `<localleader>s` / `<localleader>S` pickers include the global
workspace, any ancestor project workspaces discovered from the current
buffer, direct child repos in an enclosing higher-order project workspace,
and any `additional_workspaces` you configure.

5.7 ARCHIVING LIFECYCLE                                *clearhead-tut-archive*

Actions move through three stages before leaving the workspace entirely.

Stage 1: Active  (`<charter>.actions`)
  Open, in-progress, and blocked actions. This is the working file.

Stage 2: Completed  (`<charter>.completed.actions`)
  Completed and cancelled actions, kept for recent history and reference.
  This file accumulates over time and can be cleaned up independently.

Stage 3: Archive  (`archive/` at the workspace root)
  Permanent read-only plaintext history. When a whole charter is archived,
  its charter, action, completed-action, and sidecar files move together under
  `archive/`, preserving their paths relative to `charters/`.

Moving from Stage 1 → Stage 2 ~

Press `<localleader>a` in any active `.actions` buffer. The plugin saves the
buffer, runs:
  `clearhead archive actions --file <filename>`

Core commits the active and completed files as one durable workspace mutation.
The plugin reloads the buffer only after the CLI exits successfully. The LSP
never archives on save and exposes no archive command because an editor-owned
buffer cannot participate in the filesystem transaction.

Moving from Stage 2 → Stage 3 (charter archive) ~

This requires two steps:

  1. Set `state: Closed` in the charter's `.md` / `README.md` frontmatter.
     Jump there with `<localleader>S` and edit the file.

  2. Press `<localleader>A` in any buffer belonging to that charter.
     The plugin infers the charter name from the buffer path and runs:
       `clearhead archive charter <name>`

     What happens:
       - The charter markdown, `.actions`, `.completed.actions`, and sidecar
         files move together under the workspace `archive/` directory
       - Nested child-charter files move with their parent subtree
       - Calendar plan files remain in the workspace plan vdir

To archive all closed charters in one pass: >vim

  :ClearheadArchiveWorkspace
<
Pressing `<localleader>a` from a `.completed.actions` buffer ~

The plugin detects this case and redirects to `archive charter <name>`
rather than trying to archive an already-completed file. If the charter
is not yet marked `state: Closed`, a message guides you to set it first.

Quick reference ~

  `<localleader>a`          Archive completed items in active file
                             (or redirect to charter archive if in
                             a .completed.actions buffer)
  `<localleader>A`          Archive the whole current charter
                             (requires state: Closed in frontmatter)
  `:ClearheadArchiveWorkspace`  Archive all closed charters at once

6. KEYBINDINGS                                            *clearhead-mappings*

All mappings are buffer-local. Action-editing mappings are only active in
`.actions` files; charter-scoped navigation/archive mappings also activate in
charter markdown files under `charters/`.
Requires `nvim_default_mappings = true` (default).

Disable with: >lua

  require("clearhead").setup({ nvim_default_mappings = false })
<
`<localleader>` is `\` by default. Set your own: >vim

  let maplocalleader = ","
<

State manipulation ~

  `<localleader><space>`   Cycle state: [ ] → [-] → [=] → [x] → [_] → [ ]
  `<localleader>x`         Set Completed  `[x]` + appends `%timestamp`
  `<localleader>X`         Recursively complete action and all children
  `<localleader>-`         Set state to In Progress  `[-]`
  `<localleader>=`         Set state to Blocked      `[=]`
  `<localleader>_`         Set state to Cancelled    `[_]`
  `<localleader><bs>`      Reset state to Not Started `[ ]`

File operations ~

  `<localleader>f`   Format and normalise (LSP first; CLI normalize fallback)
  `<localleader>a`   Archive completed/cancelled actions out of current
                     file to `.completed.actions` (redirects to charter
                     archive when in a `.completed.actions` buffer;
                     requires `state: Closed` for that path)
  `<localleader>A`   Move the whole current charter under `archive/`
                     (requires `state: Closed` in charter frontmatter)
  `<localleader>C`   Close the current charter
  `<localleader>o`   Insert new `[ ]` below current line at same depth
  `>>`               Increase depth of action on current line (add `>`)
  `<<`               Decrease depth of action on current line (remove `>`)

Navigation ~

  `<localleader>i`   Open inbox
  `<localleader>p`   Open workspace data directory (netrw / oil.nvim / etc.)
  `<localleader>P`   Walk up to nearest `.clearhead/`, open `next.actions`
  `<localleader>s`   Picker: active action files across all visible workspaces
  `<localleader>S`   Picker: markdown charter documents across all visible workspaces

7. COMMANDS                                              *clearhead-commands*

These commands are always available regardless of the current filetype.

                                                       *:ClearheadInbox*
:ClearheadInbox
    Open the inbox in the current window.
    Equivalent to `<localleader>i`.

                                                    *:ClearheadWorkspace*
:ClearheadWorkspace
    Open the workspace data directory in the current window.
    Pairs well with a directory explorer (oil.nvim, snacks, netrw).
    Equivalent to `<localleader>p`.

                                                 *:ClearheadProjectRoot*
:ClearheadProjectRoot
    Walk upward from the current buffer to find the nearest `.clearhead/`
    directory, then open `charters/next.actions` inside it.
    Falls back to `:ClearheadInbox` if no `.clearhead/` is found.
    Equivalent to `<localleader>P`.

                                                       *:ClearheadDiff*
:ClearheadDiff
    Open a vertical diff split of the current buffer against itself.
    Useful for reviewing unsaved changes before writing.

                                              *:ClearheadArchiveWorkspace*
:ClearheadArchiveWorkspace
    Archive all charters whose frontmatter carries `state: Closed` in
    a single pass. Equivalent to `require("clearhead").archive_workspace()`.

                                                *:ClearheadPickActions*
:ClearheadPickActions
    Open a `vim.ui.select` picker over all active `.actions` files across
    the global workspace, ancestor project workspaces, direct child repos in
    any enclosing higher-order workspace, and configured extras. Discovery is
    recursive under `charters/`. Excludes `.completed.actions` and
    `.upcoming.actions`.
    Equivalent to `<localleader>s`.

                                               *:ClearheadPickCharters*
:ClearheadPickCharters
    Open a `vim.ui.select` picker over all markdown charter documents
    (`*.md`, `**/README.md`) across all visible workspace roots.
    Equivalent to `<localleader>S`.

                                                    *:ClearheadQuery*
:ClearheadQuery [name]
    Run a named index query and render the results as the quickfix list.
    Each entry jumps to the action in its source file (`<CR>`, |:cnext|,
    etc.); the entry's `user_data` carries the action's canonical id, the
    stable address mutation verbs act on. The list title is
    `clearhead: {name}` and the list context records the query name so a
    refresh can re-run the same query. An empty result renders an empty
    list — an empty agenda is an answer, not an error.

    [name] is the stem of a `.sparql` file saved under:
      `~/.clearhead/queries/index/`       user-global
      `<workspace>/.clearhead/queries/index/`  project-local

    Built-in named queries ~
      (none)       All open actions with source locations (default)
      agenda       The daily list: actionable now — unblocked, lowest open
                   child, scheduled or due on or before end of today.
                   Overdue items included. No undated actions.
      unscheduled  The agenda's complement for date-light projects:
                   actionable now and unplanned — no scheduled/due date
                   on the action or any ancestor. Sorted by priority.
      weekly       The horizon: everything open in the next seven days,
                   including blocked and undated work.

    Examples: >vim
      :ClearheadQuery              " all open actions
      :ClearheadQuery agenda       " today's list
      :ClearheadQuery unscheduled  " undated, actionable, by priority
      :ClearheadQuery weekly       " the week's horizon
      :ClearheadQuery my-filter    " user query at queries/index/my-filter.sparql
<
                                                    *:ClearheadTree*
:ClearheadTree [name]
    Run a named tree-family query and render its validated hierarchy in a
    read-only scratch split. [name] defaults to `work-map`, the graph-backed
    charter and open-action hierarchy.

      `<CR>`    Open the charter Markdown file or action source line
      `<Space>` Expand or collapse the current branch
      `r`       Re-run the tree query
      `q`       Close the tree split

    The view consumes `clearhead-graphd query tree [name] --format json`
    directly. Canonical identity and parentage come from graphd; Neovim only
    projects the validated nested result.

                                                   *:ClearheadGraph*
:ClearheadGraph [name]
    Run a named graph-family query and open graphd's DOT projection in a
    read-only scratch buffer with `filetype=dot`. [name] defaults to
    `dependencies`.

      `p`    Render the DOT to a temporary SVG with Graphviz and open it
      `r`    Re-run the graph query
      `q`    Close the graph buffer

    RDF remains graphd's semantic graph contract; DOT is the visualization
    language returned to the editor. The optional preview requires the `dot`
    executable from Graphviz.

    The living loop ~
                                                    *clearhead-living-loop*
    Inside the quickfix window, with `nvim_default_mappings` enabled, the
    view is alive — read → verb-by-id → re-read:

      `<localleader>x`   Complete the action under the cursor
      `<localleader>_`   Cancel the action under the cursor
      `<localleader>r`   Re-run the view's query, rebuild the list

    A verb addresses the entry's canonical id (never its line number), so
    it acts on exactly that action even after the file shifted. After the
    verb the list re-settles in place: completed work leaves, unblocked
    successors surface, and the cursor keeps its row. Verbs are
    save-gated — a modified buffer for the entry's file aborts the verb
    (the CLI mutates the file on disk; save first). Foreign quickfix
    lists are untouched: the mappings warn and do nothing.

8. LSP CAPABILITIES                                          *clearhead-lsp*

The standalone `clearhead-lsp` server attaches automatically to `.actions`
buffers when `nvim_lsp_enable = true`.

Start manually: >sh

  clearhead-lsp
<

  Capability            What it does ~
  ─────────────────────────────────────────────────────────────────────
  Completion            Date snippets for `@`, `%`, `^`: "now", "today",
                        "tomorrow", and ISO date completions

  Code Actions          Hydrate UUID (assign missing `#id`)
                        Set / backfill completion date
                        Derive creation date from UUIDv7 timestamp

  Semantic Tokens       Syntax highlighting: state, name, description,
                        priority, objective ref, context tags, all dates,
                        UUID

  Inlay Hints           Due-date countdown: "due in 3d", "due today",
                        "overdue 2d"
                        Completion age: "done 5d ago"

  Go to Definition      Jump to first occurrence of an objective or tag

  Find References       List all occurrences of an objective or context tag

  Document Formatting   Normalise: assign missing UUIDs, fix spacing,
                        sort fields into canonical order, reindent children

  Diagnostics           Lint on every keystroke: missing UUID,
                        invalid/inconsistent dates, unresolved references,
                        skipped depth levels, completed parent with open
                        children, and more (see |clearhead-lsp-diagnostics|)

  Archive Mutations     Not exposed by the LSP. Clients save the buffer, run
                        the CLI's durable mutation, then reload/close on success.

  Telemetry (on save)   Diff saved state to emit action lifecycle events

                                                  *clearhead-lsp-diagnostics*
Diagnostic codes ~

  E001  duration without do date
  E003  empty context tag
  E004  orphaned child marker (> with no parent action)
  E005  skipped hierarchy level (e.g. root → depth 2)
  E006  invalid UUID format
  I001  completed action without completion date
  I002  completion date on non-completed action
  I003  invalid priority value
  I004  duplicate UUID in workspace
  I006  fields out of canonical order
  I007  high-priority action without a do date
  I008  blocked action without a description
  I009  child has higher priority than parent
  W001  hierarchy depth exceeded
  W002  completed parent with uncompleted children
  W003  all children completed but parent is not
  W004  missing creation date
  W010  duplicate alias
  W011  ambiguous short UUID reference

                                                       *clearhead-lsp-local*
Operations that bypass the LSP (tree-sitter, no roundtrip) ~

  State cycling        Reads and replaces the `[ ]` character directly
  Smart new action     Inserts at correct depth with `^` creation date;
                       UUID filled on format-on-save
  Depth indent/dedent  Prepends or removes one `>` on the current line
  Statusline count     Completed / total via a tree-sitter query
  Completion stamp     Appends `%<timestamp>` when state transitions to `[x]`

9. STATUSLINE INTEGRATION                             *clearhead-statusline*

`require("clearhead").get_status()` returns `✓ <done>/<total>` for the
current buffer, or `""` when no actions are present.
Computed via tree-sitter — no LSP or CLI required.

lualine.nvim example: >lua

  require("lualine").setup({
    sections = {
      lualine_x = {
        {
          function()
            return require("clearhead").get_status()
          end,
          cond = function()
            return vim.bo.filetype == "actions"
          end,
        },
      },
    },
  })
<
heirline.nvim example: >lua

  local ClearheadStatus = {
    condition = function()
      return vim.bo.filetype == "actions"
    end,
    provider = function()
      return require("clearhead").get_status()
    end,
  }
<

10. LUA API                                                  *clearhead-api*

All public functions live on `require("clearhead")`. Buffer arguments accept
`0` or `nil` for the current buffer. Window arguments accept `0` for the
current window.

                                                    *clearhead.setup()*
`setup({opts})`
    Initialise the plugin. Must be called once. See |clearhead-config|.

                                               *clearhead.cycle_state()*
`cycle_state(bufnr, linenr)`
    Cycle the state on the given 0-indexed line in order:
    `[ ]` → `[-]` → `[=]` → `[x]` → `[_]` → `[ ]`
    Appends `%<timestamp>` when cycling into `[x]`.

                                                *clearhead.set_state()*
`set_state(bufnr, linenr, state)`
    Set the state on `linenr` to `state` (one of `" "`, `"-"`, `"="`,
    `"x"`, `"_"`). Appends `%<timestamp>` when state is `"x"`.

                                           *clearhead.set_state_tree()*
`set_state_tree(bufnr, linenr, state)`
    Set the state on `linenr` and recursively on all child actions that
    fall within the same action node. Useful for closing a whole subtree.

                                           *clearhead.smart_new_action()*
`smart_new_action(bufnr, linenr)`
    Insert a new `[ ]` line below `linenr` at the same depth as the
    current action. Adds a `^<timestamp>` and enters insert mode.
    UUID is assigned on next save by format-on-save.

                                              *clearhead.indent_action()*
`indent_action(bufnr, linenr)`
    Increase the depth of the action on `linenr` by one. Prepends a `>`
    marker directly before the existing marker sequence. The LSP validates
    the resulting depth on next save.

                                              *clearhead.dedent_action()*
`dedent_action(bufnr, linenr)`
    Decrease the depth of the action on `linenr` by one. Removes one `>`
    marker. Notifies and does nothing when the action is already at root.

                                                   *clearhead.archive()*
`archive([bufnr])`
    Sweep completed and cancelled action trees from `bufnr` to
    `<charter>.completed.actions`. Saves the buffer, invokes the CLI's durable
    archive operation, and reloads only after success.

    When `bufnr` points to a `.completed.actions` file the function redirects
    to `archive charter --file <filename>` (see |clearhead.archive_charter()|)
    and closes the moved buffer only after success.

                                           *clearhead.archive_charter()*
`archive_charter([{opts}])`
    Archive the charter inferred from the current buffer path.
    Requires `state: Closed` in the charter's frontmatter.

    opts ~
      `force`    boolean  Archive even if open actions remain (default: false)
      `dry_run`  boolean  Print plan without writing (default: false)

                                         *clearhead.archive_workspace()*
`archive_workspace([{opts}])`
    Sweep all charters carrying `state: Closed` in one pass.
    Accepts the same opts as |clearhead.archive_charter()|.

                                                   *clearhead.format()*
`format([bufnr])`
    Format `bufnr` via the attached LSP. The formatter respects the
    current buffer indentation settings (`expandtab`, `shiftwidth`,
    `tabstop`, `softtabstop`); `clearhead.nvim` defaults `.actions`
    buffers to 4-space indentation unless overridden in `setup()`.
    If no client is attached yet but the server is running, attaches
    first then formats. Falls back to |clearhead.normalize()| when
    `nvim_auto_normalize = true`.

                                                *clearhead.normalize()*
`normalize([bufnr])`
    Run `clearhead normalize file --write` to assign missing UUIDs and
    fix spacing. Reloads the buffer via `checktime` on success.
    No-ops if the buffer has no backing file or the binary is not found.

                                               *clearhead.get_status()*
`get_status()`
    Returns `"✓ <done>/<total>"` for the current buffer via tree-sitter,
    or `""` if no actions are present. See |clearhead-statusline|.

                                           *clearhead.pick_action_file()*
`pick_action_file()`
    Open a `vim.ui.select` picker over all active `.actions` files across
    the global workspace, ancestor project workspaces, direct child repos in
    any enclosing higher-order workspace, and configured extras. Discovery is
    recursive under `charters/`. Excludes `.completed.actions` and
    `.upcoming.actions`.
    With multiple scopes each entry is prefixed `[scope]` for fuzzy search.
    Delegates to telescope / fzf-lua / snacks if installed.

                                            *clearhead.pick_charter_doc()*
`pick_charter_doc()`
    Open a `vim.ui.select` picker over all markdown charter documents
    (`*.md`, `**/README.md`) across all visible workspace roots.
    Discovery is recursive under `charters/`. Directory-form charters display
    as the directory name; root `charters/next.actions` entries display as the
    workspace / project name.

                                           *clearhead.get_conform_opts()*
`get_conform_opts()`
    Returns the conform.nvim formatter table for the `actions` filetype.
    See |clearhead-conform|.

                                                   *clearhead.open_inbox()*
`open_inbox(winnr)`
    Open the inbox file in window `winnr`. Uses `nvim_inbox_file` if set,
    otherwise `data_dir/charters/<default_file>`.

                                               *clearhead.open_workspace()*
`open_workspace(winnr)`
    Open the workspace data directory in window `winnr`.

                                            *clearhead.open_project_root()*
`open_project_root(winnr)`
    Walk upward from the buffer in `winnr` to find the nearest
    `.clearhead/`, then open `charters/next.actions` inside it.
    Falls back to |clearhead.open_inbox()| if none is found.

                                                  *clearhead.run_query()*
`run_query({name}, {callback})`
    Run a named index query and pass the parsed rows to `callback(rows)`.
    Shells out directly to `clearhead-graphd query index [name]` asynchronously
    and requests the index JSON-LD contract explicitly.

    `name` (string|nil) — named query variant, e.g. `"agenda"`. Pass `nil`
    for the default (all open actions with source locations).

    `callback` (function) — called with a list of row tables on success.
    Each row contains at minimum: >

      row.id            string   canonical action identity (`id` client surface)
      row.name          string   action name
      row.status        string   "NotStarted" | "InProgress" | "Blocked" | …
      row.source_file   string   path relative to charter_root
      row.source_line   integer  1-based line number
      row.charter_root  string   absolute path to the workspace charter root
<
    Named queries may return additional columns (e.g. `scheduled_at`,
    `due_date`). Extra fields are passed through as-is.

    The callback is responsible for display. Example using `vim.ui.select`: >lua

      require("clearhead").run_query("agenda", function(rows)
        vim.ui.select(rows, {
          prompt = "agenda",
          format_item = function(r) return r.name .. " [" .. r.status .. "]" end,
        }, function(choice)
          if choice then
            vim.cmd("edit " .. vim.fn.fnameescape(
              choice.charter_root .. "/" .. choice.source_file))
            vim.api.nvim_win_set_cursor(0, { tonumber(choice.source_line), 0 })
          end
        end)
      end)
<
    Errors (binary not found, graphd failure, JSON parse failure) are reported
    via `vim.notify` at `ERROR` level; the callback is not called.

                                                   *clearhead.open_tree()*
`open_tree({name})`
    Run a named tree query and render it in a read-only scratch split — the
    Lua entry point behind |:ClearheadTree|. `name` defaults to `work-map`.
    Charter and action locators open their canonical source files; action
    locators also carry the source line.

                                                *clearhead.refresh_tree()*
`refresh_tree()`
    Re-run the query behind the current tree buffer while preserving expanded
    and collapsed identities.

                                                  *clearhead.open_graph()*
`open_graph({name})`
    Run a named graph query and open its DOT projection — the Lua entry point
    behind |:ClearheadGraph|. `name` defaults to `dependencies`.

                                               *clearhead.refresh_graph()*
`refresh_graph()`
    Re-run the query behind the current DOT buffer.

                                               *clearhead.preview_graph()*
`preview_graph()`
    Render the current DOT graph to a temporary SVG with Graphviz and open it
    through `vim.ui.open()`.

                                                  *clearhead.open_view()*
`open_view({name})`
    Run a named index query and render it as the quickfix list — the Lua
    entry point behind |:ClearheadQuery|. Each row maps to one entry:
    `charter_root/source_file` and `source_line` become the jump target,
    the composed `name [status] due:…` becomes the display text, and the
    canonical `id` goes into the entry's `user_data` as the stable address
    for mutation verbs.

    `name` (string|nil) — named query variant, e.g. `"agenda"`. Pass `nil`
    for the default.

                                               *clearhead.refresh_view()*
`refresh_view()`
    Re-run the current clearhead view's query and rebuild the quickfix
    list in place, keeping the cursor's row (clamped to the new length).
    Warns if the current list is not a clearhead view.

                                               *clearhead.act_on_entry()*
`act_on_entry({verb})`
    Fire a mutation verb on the quickfix entry under the cursor by its
    canonical id, then |clearhead.refresh_view()|. See
    |clearhead-living-loop| for gating and re-settle behavior.

    `verb` (string) — `"complete"` or `"cancel"`.

    The CLI's typed result (query_output.md, "Errors as data") drives the
    outcome: `completed`/`cancelled` notify and re-settle; an
    `already-closed` or `not-found` (stale entry) result notifies and
    refreshes rather than guessing.

11. CONFORM.NVIM INTEGRATION                             *clearhead-conform*

`get_conform_opts()` returns a formatter config table ready to merge into
conform.nvim's setup: >lua

  local clearhead = require("clearhead")

  require("conform").setup({
    formatters_by_ft = clearhead.get_conform_opts().formatters_by_ft,
    formatters       = clearhead.get_conform_opts().formatters,
  })
<
This registers `clearhead` as the formatter for the `actions` filetype,
running `clearhead format file $FILENAME` on save.

Note: when `nvim_lsp_enable = true` (default), LSP formatting takes
precedence. The conform integration is only needed if you prefer conform's
workflow or have disabled the LSP.
